# AGENTS.md — Local Agent Service

## 服务定位与责任边界

`local-agent-service` 是运行在用户本机 macOS（当前主要目标为 MacBook）的长任务 AI 服务，属于 `vocal-saga` 仓库，但**不是 Cloudflare Worker 的一部分，也不能按 Cloudflare Worker 的资源与生命周期假设设计**。它由 Node.js 运行，默认仅监听 `127.0.0.1:8789`，通过本机 HTTP API 与 `fanyi-extension` 协作。

本服务面向需要更高质量、较长上下文、持久化状态和 Agent 编排的任务。对于文档与小说翻译，**翻译质量优先于响应速度**；允许长时间运行、分批执行、审校、候选比较和选择性返工，但必须有可观测状态、持久化进度、可恢复性和明确的停止边界。

## 本服务负责

- 调用本机可用的 AI Runtime/Agent，例如 Workbuddy/CodeBuddy SDK、OpenCode CLI；管理 Provider/模型选择、会话边界、工具调用、超时和失败分类。
- 完整支持 EPUB/PDF 等文档翻译工作流：项目与来源版本、稳定分段、批次执行、断点恢复、候选译文、采纳译文、人工修订、审校发现和事件记录。
- 维护文档级上下文：书籍/项目记忆、章节与场景摘要、术语表、实体映射、人物声音档案、人物关系与称谓规则、已确认的译例。
- 运行按任务类型选择的 Pipeline 和 Prompt，包括初译、结构/忠实度检查、术语一致性检查、文风/人物声音审校、候选比较和有条件的局部返工。
- 将任务状态、阶段事件、错误、耗时、Provider/模型元数据和持久化检查点提供给扩展，使 UI 关闭或刷新不致丢失已经保存的项目进度。
- 为长期质量改进提供可重复的离线评测、黄金样本、回归测试和 Prompt/策略版本记录。

## 不负责

- 不承担浏览器 UI、页面 DOM 操作、浏览器权限、网页布局恢复或扩展生命周期管理；这些属于 `fanyi-extension`。
- 不依赖 Cloudflare Worker 的执行时限、内存或计算预算，也不将本机服务打包成 Worker Handler。
- 不将所有翻译请求都强制升级为长时间 Agent 任务。普通网页段落或短文本的低延迟翻译应使用 Cloud API 或适合的轻量路径，除非用户明确选择本机服务。
- 不以无条件多 Agent/多轮审校作为默认。额外调用必须针对预期质量收益、风险或检测到的问题；应允许简单任务走轻量 Pipeline。

## 统一执行管线与任务策略

本服务对所有本地长文翻译只维护一条**项目级执行管线**：阅读页的继续翻译/强制重译、Agent Workspace、CLI 和项目 API 必须进入同一套 Document Project / Run 生命周期，由 `startProjectTranslationRun → executeRun → processBatch` 统一执行。界面入口只能选择当前页/章节/选定片段/全部或过期片段等 Run scope，不得自行执行另一套本地翻译循环、另造人物记忆更新机制或在扩展端直接修改项目记忆。

统一的是调度、持久化、恢复、结构验证、候选译文、审校、事件与质量审计边界，不是把文学、技术文档和短文本强行使用同一份 Prompt。任务差异必须表达为同一管线中的明确策略/Prompt 配置，而不是按入口分叉。阅读页（截图中的“继续翻译下一待译页/强制重译当前页”）也必须通过项目 API 创建或恢复 Run；不允许仅 Agent Workspace 才享有 TranslationBrief、上下文增量或质量检查。

文学初译的统一响应包含 `translations` 和有界 `context_delta`。服务端独立验收两部分：译文按 segment ID 校验和保存；上下文增量只有在引用当前批次真实 segment ID、连续原文引文可验证，且译文提及的 target surface 确实存在时才接受。上下文增量在同一波次冻结，不得影响同波其他批次；波次完成后按原文 ordinal 合并，下一波才可读到候选。所有模型新增内容保持 suggested/candidate，不能自称 confirmed，也不能覆盖人工确认记忆或被采纳的译文。详细契约见 [本地统一翻译 Pipeline 架构](../docs/TRANSLATION_PIPELINE.md) 和 [ADR-0001](../docs/adr/0001-unified-local-translation-context-delta.md)。

| 任务类型 | 目标与策略 | 建议 Pipeline |
|---|---|---|
| 小说/文学长文 | 最高翻译质量；人物声音、叙述视角、语气、关系和跨章节一致性 | 加载项目记忆与章节上下文 → 初译 → 忠实度/遗漏检查 → 人物声音与文风检查 → 术语/称谓一致性检查 → 仅对有问题片段返工 → 持久化采纳结果 |
| 一般 EPUB/PDF/长文档 | 完整、准确、术语一致，保留结构与可恢复性 | 文档解析与稳定分段 → 文档/章节上下文准备 → 分批初译 → 结构与完整性验证 → 风险片段审校 → 选择性返工 → 导出/同步 |
| 技术文章或网页长文 | 忠实、术语和代码一致，避免不必要的文学润色 | 轻量上下文 → 分块翻译 → 术语/格式检查 → 对异常块定向重试 |
| 短文本/选区 | 简洁、直接、快速完成，不引入长篇规划 | 单次翻译 → 结果结构与空输出检查；仅在失败时进行有限重试 |
| 需要复杂工具的翻译研究/编辑任务 | 允许多步骤与 Agent 工具调用，结果可追踪 | 任务计划 → 有界工具调用 → 证据/候选记录 → 结果验证 → 汇总与持久化 |

这些是策略模板，不是硬编码的唯一流程。根据源语言、目标语言、文体、文档结构、用户质量选项、模型能力与实际失败信号选择或调整步骤。

## 原始文档解析与 Context Graph 边界

- EPUB/DOCX/PDF 等原始文件的解析和预处理必须位于 local-agent-service，不得要求 fanyi-extension 先将整本书拆成片段；本机服务提供独立 CLI/API 入口。本约束不意味着可以顺带修改扩展，本项目任务若明确要求不动扩展，就只提交服务端变更。
- 支持纯文本 EPUB、DOCX、TXT、Markdown、HTML，以及带文本层的 PDF。PDF 通过 Poppler `pdftotext` 做文字提取；当前不实现 OCR，也不能把“未提取到文字”静默视作成功。
- EPUB 按 OPF manifest/spine 顺序读取，保留章节/内容路径、标题与稳定片段 ID。解析必须有文件大小、解压大小、片段数、超时及路径安全边界；不得将 ZIP 条目解压到用户可控的任意路径。
- Context Graph 是来源版本级的持久化状态，SQLite 为事实来源。模型生成的人物、别名、实体、关系与摘要先作为候选；证据必须包含稳定 segment ID 和能在对应原文片段中验证的连续引文。模型自称“确认”不能代替证据校验或人工确认。
- 全书图谱、原文证据、章节摘要与人物/关系候选必须留在服务端；不得复制到扩展 LiteraryMemory。扩展轮询使用轻量 /context-graph/status 投影，不轮询完整节点/证据载荷。
- 文学 Run 的来源版本、分析版本和语言方向门禁由 executeRun 在进入 running 前执行；服务端自动启动并等待所需 Context Graph。扩展负责提交 Run、展示进度和提供显式重新分析入口，不实现常规流程的第二套预处理门禁。
- 抽样不得只取开头、章节标题或最近章节。长文档至少覆盖开头/中部/结尾、分布式章节样本以及对白或专名较密集的片段；其余章节可以先生成抽取式摘要，再逐步补充模型摘要。
- 小说预分析必须先对全部 source segments 做确定性低成本扫描，再进行自适应抽样。主质量基线按英文原文翻译成中文设计；扫描结果包括章节分布、英文首字母大写姓名候选、对白信号、重复英文句子/引语线索；长文默认最多 72 个样本，单样本最多 850 个原文字符，短文档在预算内全量采样。
- 长文样本计划需保留开头/中部/末尾、跨章节分布，并尝试对高重要性名称候选补采样早期/中期/后期提及，再补充重复表达与对白密集片段。抽样理由与扫描计数应持久化到 Context Graph run progress，便于观察覆盖范围；不得只记录一个 sampleCount。
- 英文姓名扫描是首字母大写启发式，不是 NER：句首普通词可能被误判，非典型拼写、化名、称谓与同名异人也可能漏检。扫描统计和候选名称只能指导采样，不是事实；每个被保存的图谱结论仍需来自被采样片段的可验证原文引文。证据查询应返回 source segment ID、章节路径和原文顺序。
- 维护合成小说质量回归集，至少覆盖漏译、名称/别名漂移、重复台词不一致、后文揭秘泄漏；人物声音需另有人工盲审样例，不能用自动流畅度或一个总分代替。合成样本只能验证确定性规则和失败控制，不得冒称是真实模型效果基线。
- 翻译时动态检索只注入当前批次真正匹配的人物/实体、相关关系与当前及之前章节摘要；禁止将整本书的所有记忆无差别塞入每个 Prompt，禁止注入后续章节摘要造成剧透。上下文必须设预算并有可观测的命中计数。
- Context Graph 的来源版本、节点/边状态、结构化属性、证据和章节摘要必须影响文学运行指纹；图谱预处理或人工审核不能在翻译 Run 执行期间修改图谱，避免同一个 Run 的不同批次看到不同版本的上下文。
- 每个文学批次必须构造并持久化一个版本固定的 TranslationBrief；初译、accuracy/terminology Reviewer 和 style/character-voice Reviewer 共用同一快照。快照包括受时间边界过滤的 glossary、前文、Context Graph 与 voice context，并记录 source/prompt/memory revision、source segment IDs、context hash、context size、知识边界和检索条目计数。检索按原文证据、时间边界、相关性与冗余决定注入内容，不按固定画像数、译例数或 18,000 字符目标静默裁剪关键上下文；当前序列化字符上限是 1,000,000 的异常安全阈值，不是检索目标。若 Provider 的实际上下文窗口拒绝请求，应显式记录该限制，而不是悄悄改写 TranslationBrief；Reviewer 不得重建更宽的前文上下文。
- 时间边界按来源 ordinal 定义，而不只按章节名：图谱节点/关系只有在所有存储证据都早于当前批次第一个 source segment 时才能注入。只允许前两章的完整摘要；当前章节只允许用批次之前的原文片段构建前缀摘要，禁止使用包含当前批次之后内容的完整章节摘要。
- 质量审计必须能在整书范围内定位缺失译文、已确认术语漂移、重复原文表达译法差异，以及已有 Reviewer 标注的人物声线/文风问题。启发式发现是人工复核入口，不得自动统一重复表达，也不得自动应用 style finding。
- 定点返工必须创建新的 selected-ID Run，不覆盖已采纳/人工译文；人工采纳仍是唯一提升候选的显式闸门。返工报告与 Run 必须保存来源版本及父运行关联，来源变化后旧报告不得发起返工。
- M4 的前后对照必须验证相同来源版本、源/目标语言和精确的 segment ID 集合，拒绝比较仍在运行/暂停/取消的任务。记录 model calls、已知 prompt 字符和已知调用时延；若 Provider 没提供 token/billing 数据，不得推算或声称真实费用。A/B 映射在每个样本完成 overall 人工盲评前不得披露。
- CLI、API 和 README/AGENTS 必须一致。服务端直读入口不会自动改变扩展的现有阅读流程；没有对应的扩展集成代码就不得声称扩展已开始使用新导入器。

## Prompt 设计规则

1. 按任务类型维护独立、可版本化的 Prompt 与策略；不得用单一“通用翻译 Prompt”处理短文本、技术文档和小说。
2. 小说 Prompt 应明确叙述视角、人物身份、语域、口头禅、句式偏好、称谓和人物关系变化；人物声音资料是指导约束，不是机械地把所有台词改成夸张口癖。
3. 技术文档 Prompt 应优先保证事实、术语、标识符、代码、表格和结构忠实，不应套用文学润色策略。
4. 初译、审校、候选评估应有不同的任务指令。Reviewer 应指出可定位、可验证的问题，并避免把个人风格偏好误判为事实错误。
5. Prompt、模型、语言方向、术语表/项目记忆版本及 Pipeline 版本必须进入适当的运行记录和缓存指纹。关键输入变化时应失效相关缓存。
6. 只将必要的章节/场景摘要、相关人物卡和相关术语传入当前批次；避免把全书原文或完整运行历史重复塞入每次调用。
7. JSON/结构化输出必须进行解析、完整性和语义验收；解析失败或被截断的内容不能当成成功译文缓存或采纳。

## 质量优先，但必须可控

- 对长文档可以采用分批并发、独立会话、Reviewer 队列、候选比较与局部返工；并发度必须考虑本机内存、模型 Provider 限额和会话隔离，不能假设越多并发质量越高。
- 以质量收益决定额外调用：优先复核遗漏、误译、术语冲突、人物声音漂移和结构损坏等高价值问题，而不是对每个段落机械地调用所有 Reviewer。
- 长任务必须支持持久化检查点、可重入/幂等的批次处理、取消信号和明确的停止边界。停止后不能继续悄悄发起新的模型调用。
- 所有模型与工具调用都应记录阶段、耗时、Provider/model、输入版本、结果状态和错误类别；日志应便于按 request/run ID 关联，不得记录密钥。
- 缓存命中必须验证原文版本、语言方向、Prompt/Pipeline 版本、模型配置以及相关项目记忆版本；不得让旧缓存覆盖人工修订。
- 文档任务的“完成”必须由持久化状态和验收结果决定，不能仅以某个请求返回 HTTP 200 或某个批次结束为准。

## 阅读页与 Agent Workspace 一致性约束

- 阅读页“继续翻译下一页/下几页”“强制重译当前页”和 Workspace/API/CLI 必须调用同一 project run executor；新增 UI 操作只能映射到 scope 或策略配置，不得新增平行翻译实现。
- 服务端统一生成并持久化 TranslationBrief，统一处理结构化初译、证据校验、候选提交、审校、上下文增量、取消/恢复与质量审计。扩展负责显示进度和呈现已保存状态，不负责合并模型上下文增量。
- 对局部/强制重译同样使用统一契约；上下文记忆仍按来源 ordinal 过滤，不得因“强制”绕过上下文证据、来源版本或人工采纳边界。
- 修改阅读页触发路径时，必须增加覆盖 project API 到同一 Run executor 的回归测试，并核对事件/Run 状态而不能只验证按钮反馈。

## 安全与运行约束

- 默认只监听 loopback；不得通过局域网、反向代理或隧道公开本机 Agent API。
- 遵守输入大小、存储配额、超时和清理策略。长任务可以长，但不能无限制积累上下文、并发任务、缓存或日志。
- 不得静默回退到 Cloud API，也不得将远程结果标记成本机 Agent 结果。Provider 不可用时应明确报告失败或执行经过用户/产品策略允许的备选方案。
- 对 API、项目、运行、批次和候选的状态变更增加测试；尤其覆盖重启恢复、重复提交、取消、部分完成、缓存失效、损坏 JSON 和模型输出不完整。
- 在修改前先阅读相关 ADR、README、现有实现和测试；优先复用已有 Document Project、SQLite、事件与恢复机制，不另造平行体系。

## 全流程审计与原始来源保全（ADR-0002）

- 必须遵守 [ADR-0002](../docs/adr/0002-local-translation-audit-ledger-and-source-preservation.md)。最终译文、当前状态、日志摘要都不能替代逐次调用账本。
- 完整分段原文必须持久化；存在原始文件时保存原始字节、SHA-256 和服务管理的数据路径。只有 segments 的项目必须显式标记为 segments-only。
- 初译、定向重试、每种 Reviewer、全书分析和质量修复都要保存实际输入快照、输出、校验、模型/Provider、阶段、时间、错误与重试关联。审校输入须能重建对应原文和候选译文。
- 重要状态转换必须持久化；失败的审计写入不能静默降级为成功。重试、修订和人工采纳不得覆盖历史证据。
- 设置页路径必须来自服务实际运行配置，不得由扩展猜测 home 路径，也不得暴露密钥。
## 自动化优先：默认完成闭环，人工只处理例外

- **产品目标是至少 99% 的常规文档/小说翻译在启动后不需要用户中途确认、逐项审稿或修改规则**。开始、停止和用户主动修改属于正常控制；不得让用户为每批、每个 Reviewer、每条候选记忆或每项审计发现充当调度器。
- 默认编排应自动衔接：必要的全书预处理 → 分批初译 → 结构/缺失验证 → 准确性与术语审校 → 文学模式下的人物声音/文风审校 → 合格结果自动保存/采纳 → 全书质量审计 → 对高置信、可验证的问题进行有界定点修复 → 最终状态与少量未解决例外汇总。按预期收益、模型成本和错误风险限制额外调用，不对每段机械增加所有 Reviewer。
- 服务端应在验证后自动调用既有的候选采纳/状态转换机制，而不是要求用户为正常输出点击“确认”。保留 candidate 与 accepted 的数据边界、版本校验和原始证据，不可直接覆盖同来源版本的人工修订。自动采纳是系统策略执行，不得在审计记录中冒称“用户确认”。
- 记忆提取与升格采用证据规则自动判断：验证稳定 segment ID、连续原文证据、来源版本、时间边界、独立佐证和冲突情况。需要弱提示的候选可以继续以低权重参与上下文，不必等待人工点击；只有满足明确的机器验证规则时才可作为强约束使用。**机器验证、自动启用、用户确认是不同状态**，不得混用同一个状态字段表达。已有 schema 若无法区分，先提出向后兼容的状态迁移方案。
- 对审校发现分类处置，而不是把全部发现变成人工审批队列：结构/缺译/无效输出在有限重试后自动补齐；与单一已验证规范映射一致的确定性问题可自动返工；英文残留、重复表达差异和文风问题先结合上下文由 Reviewer 判断，置信度足够时自动产生并采纳修订；纯风格偏好或证据不足的发现作为非阻塞提示保留，默认不逐项打断用户。自动修复须创建可追踪的新结果/Run，不得覆盖历史。
- 有冲突时不要任意挑选胜者。两个用户固定的规范映射矛盾、来源版本变化、证据失效或来源归属无法可靠判定时，采用安全的保守策略（例如不强制替换名称、保留原译文、跳过该条记忆）并继续处理其余内容；只有不存在安全继续方案、数据/权限边界将被破坏，或要执行不可逆操作时才请求用户决策。
- Reviewer 或记忆提取失败时，除非结果结构/来源关联本身无法保证安全，否则应保留已验证译文、进行有限重试、记录原因并继续其他批次。任务完成状态必须准确区分完整、部分完成和失败，不得为了达到自动化比例把未完成说成成功。
- 所有自动决策都要可解释、可审计、可撤销。记录来源/Prompt/记忆 revision、Reviewer 输入输出、发现分类、自动应用理由、修改前后快照与失败原因；保留用户原始修订和已确认记忆。评价自动化不仅看“少点按钮”，还要覆盖：无人工干预完成率、每千段人工介入次数、自动修复回退率、漏修率，以及未解决问题是否被明确保留。
- 任何新增的确认/批准步骤必须在设计和 PR 中解释：为什么无法通过证据校验、保守回退、可撤销自动处理或非阻塞异常来解决；并为常规任务不中断添加回归测试。
