## `POST /fanyi/page` 改为存客户端 `contentHash`（结构指纹）

配合扩展端修复 a16z.news「翻译内容和原文对不上」（缓存里的 block id 映射过期 →
译文贴到错误的块上）。

**`lib/app.ts` 的改动**：`contentHash` 不再无条件 `String(simpleHash(html))`：

```ts
const contentHash =
  typeof body.contentHash === 'string' && body.contentHash.length > 0
    ? body.contentHash            // 扩展端结构指纹 "b1:h3|b2:p|..."
    : String(simpleHash(html));   // 旧版扩展没传 → 向后兼容
```

⚠️ **不能从 `html` 重新推导**：指纹是字符串、`simpleHash` 是数字，两者永不相等，
`/check` 会永远 410、缓存再也不命中。

**契约（两端）**：
- `/fanyi/page/check`：`clientContentHash` ≠ 存库的 `content_hash` → **410**（客户端按
  「未命中」处理，不是错误）；存库 hash 为空/NULL → **204 未命中**（那些行来自
  `/translate/url-page`，block id 是服务端自己分配的，编号体系与扩展端不同）。
- 指纹 = `id:tag` 序列（文档序），**不含文本** —— 点赞数 `142→184` 这类原地改文案不应
  让整页缓存失效；结构性变化（插入/删除/重排块）必然改变该序列。
- 逐块兜底校验在扩展端（`applyServerTranslatedHtml`），不在这里。

**测试**：`tests/appRoutes.test.ts` 新增 6 个用例；`createMockDb()` 增加 `_lastInsertArgs`
（记录最近一次 INSERT 的 bind 参数）用于断言写入的 `content_hash`。
mock DB 的 `first`/`run` 只按 `url+source+target` 匹配，忽略 `content_hash` —— 真实 SQL 也是
先按 url+lang 取最新一条再在代码里比对，所以 mock 行为与线上一致。

**验证**：`vitest run` 64 文件 / 842 通过；`tsc --noEmit` 与 `tsc -p tsconfig.lib.json`
干净；`scripts/check-sync.ts` 20/20 PASS（`lib/app.ts` 不是 sync pair）。
