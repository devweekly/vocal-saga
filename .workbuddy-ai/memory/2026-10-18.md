## 把 local-agent-service 通过 Cloudflare Tunnel 暴露到公网

目标：本机 Node + SQLite + CLI Agent 服务（`127.0.0.1:8789`）需要公网访问。
Worker 那条路不适用 —— 服务依赖 Node 运行时和本机 CLI，只能隧道。

### 改动

| 文件 | 改动 |
|---|---|
| `src/config.ts` | 新增 `ALLOWED_HOSTS`（读 `LOCAL_AGENT_ALLOWED_HOSTS`，逗号分隔，小写） |
| `src/middleware.ts` | 新增 `isAllowedHost(host, allowedHosts)` + `assertExposureIsSafe(hosts, token)` |
| `src/server.ts` | Host 校验从 `isLoopbackHost` 换成 `isAllowedHost`；启动时先跑 `assertExposureIsSafe` |

| `.env` | 已生成（gitignore 覆盖），含 token 与 `LOCAL_AGENT_ALLOWED_HOSTS=local.sunxiunan.com` |
| `.env.example` / `README.md` | 补 `LOCAL_AGENT_ALLOWED_HOSTS` 说明与「暴露到公网」整节 |

### 关键设计决定

- **监听地址仍是 loopback**。隧道从本机连进来，不需要改 `LOCAL_AGENT_HOST`；
  对外开放只靠 Host 白名单，避免服务直接监听局域网。
- **白名单非空 + token 为空 → 启动直接抛错**。不做「忘了设 token 也照常跑」的降级，
  否则等于把本机执行入口开放给任何人。
- 通配实现用 `.example.com` 后缀比较，`evil-example.com` / `notexample.com` 不会被误放行
  （测试专门钉了这条）。

### 验证

- `npm run typecheck` 干净
- `npm test` **138/138**
- 真实 quick tunnel 端到端 **3/3**：无 token → 401、正确 token → 200、错误 token → 401
  （脚本 `/tmp/verify-tunnel3.mjs`，用 curl 而非 Node fetch）

### 环境坑（下次别再踩）

1. **沙箱代理挡 CONNECT**：`curl` 默认读 `HTTPS_PROXY`，访问 trycloudflare 会拿到
   `curl: (56) CONNECT tunnel failed, response 502` —— 那是沙箱代理的响应，不是 Cloudflare。
   必须加 `--noproxy '*'`。
2. **Node fetch 到 quick tunnel 域名直接 `fetch failed`**，curl 正常。诊断公网侧用 curl。
3. **本机 DNS 对新生成的 `*.trycloudflare.com` 子域返回 NXDOMAIN**（路由器 192.168.31.1
   负缓存 / 传播慢）。绕过：`curl --resolve <host>:443:104.16.230.132` 钉到 CF anycast IP。
4. **quick tunnel 首个请求常返回 530**（边缘未就绪），要当瞬态重试，不能当被测行为。
5. `cloudflared` 自己会打印大量 precheck 日志淹没错误，过滤时排除含 `|  ` 的行。

### 未解决 / 已知限制

- **Cloudflare 单请求 100 秒上限**：文学审校实测 49s 尚可，整章翻译必挂 524。
  要支持需给响应加 SSE 心跳或改 job + 轮询 —— 架构改动，未做。
- **请求体 100 MB 上限**（CF 免费/Pro）与 `MAX_DOCUMENT_BODY_BYTES = 100 MiB` 基本持平。
- 命名隧道需用户手动 `cloudflared tunnel login`（浏览器授权），脚本只检测并提示。

## 修「无法准备文档 workspace：[object Object]」

**根因两层，缺一不可**：

1. 实际故障：扩展没带 token → 本机服务 401。
2. 显示缺陷：`documentWorkspaceClient.ts:106` 是

`popup/App.vue:273` 早就写对了（`payload.error?.message || payload.error`），
只有 workspace 客户端漏了 —— 说明这是**同类错误处理在不同文件里的不一致**，
不是单点笔误。

**修复**：`documentWorkspaceClient.ts` 新增 `describeWorkspaceFailure()`，
兼容嵌套 `{error:{message}}`、扁平 `{error:'str'}`，都取不到才回退 HTTP 状态。
新增 `src/__tests__/documentWorkspaceClient.test.ts` 5 项。

**注意**：扩展 `npm run compile`（vue-tsc）有**大量预存类型错误**
（`shardedStorage.ts`、`translationQueue.ts`、`youtube-injector.content`），
与本次改动无关，不要误判成自己引入的。

## 更深一层：404 判定靠字符串匹配（真正的「该新建却报错」）

`App.vue:3386` 原本：

```ts
if (!(error instanceof Error) || !/HTTP 404/.test(error.message)) throw error;
```

但服务端 404 返回的是**扁平中文文案**（`projectRoutes.ts:113`）：

```
HTTP 404 {"error":"找不到文档项目或项目已归档"}
```

`workspaceApi` 抛的 message 就是这个文案 —— **不含 `HTTP 404`**，正则永远不命中。
于是「IndexedDB 映射指向已被删除/归档的项目」被当成未知故障抛出，
本该走创建分支重建项目，实际直接报错退出。已用 curl 复现确认。

**修复**：`workspaceApi` 改抛 `WorkspaceApiError`（带 `status`），
`App.vue:3386` 与 `DocumentAgentWorkspace.vue:601` 都改成按 `status === 404` 判断。

教训：**不要用错误文案匹配 HTTP 状态码**。文案是给人看的，随时会改；
状态码必须走结构化字段。同类隐患在 `youtube/provider.ts:393`、`chunkTranslation.ts:171-175`
（那是远程 API 自己拼的 message，属于另一套体系，未动）。

## 修正：token 只约束非 loopback，本机默认不需要

上一版把 `authorize()` 写成「只要设了 LOCAL_TOKEN 就校验所有请求」，导致本机
`127.0.0.1` 也被要求带 token —— 扩展默认不填 token，于是「无法准备文档 workspace：
本机服务 Token 不正确或未提供」。这是**上一轮暴露改造引入的回归**，本机体验被公网需求污染。

**现在的判定顺序（顺序本身是安全关键）**：

```ts
if (isLoopbackHost(requestHostname(req))) return true;  // 先放行本机
if (!LOCAL_TOKEN) return false;                          // 再判 token 是否为空
// 最后比对 token
```

如果顺序反过来（先判 `!LOCAL_TOKEN → return true`），未设 token 时公网会直接放行。
`tests/exposure.test.mjs` 里两条 loopback 断言钉住了这个行为：
loopback 无 token → 200，loopback 错误 token → 200。

安全论证：loopback 免 token 不降低防护。浏览器发起的跨源请求由 CORS 拦（只允许
extension origin）；DNS rebinding 由 Host 白名单拦；能直连 127.0.0.1 并伪造 Host
的已经是本机进程，本来就有全部权限。

**代价**：本机不再享受 token 保护。这是有意的取舍 —— 默认配置必须开箱可用，
token 的定位是「公网访问凭证」，不是「本机访问凭证」。

## 功能：workbuddy 默认模型自动选「确认免费」的 deepseek-v4.1-flash

**需求**：provider=workbuddy 且未显式配置模型时，若模型目录里同时存在 `gpt-*` 与
`deepseek-v4.1-flash`，且后者费率为 0，就用它。

### 实验结论（关键，下次别重查）

- **model list 来源**：CodeBuddy 的产品配置，顶层 `models` 数组（本机 27 个）。
- **费率字段是 `credits`**，三种形态：`"x0.00"`（免费）、`"x0.34 credits"`（带单位）、
  `""`（未填，如 `default-model`）。不是 price / cost / rate。
- **读取优先级**：
  1. `ACC_PRODUCT_CONFIG_PATH` 指向的明文 JSON（WorkBuddy 注入，形如
     `/var/folders/.../T/workbuddy-product-spill-*/acc-product-config-v3.json`）
  2. `~/.codebuddy/local_storage/entry_*.info` —— 格式是 `JSON 字符串 → base64 → gzip → 配置 JSON`
- `codebuddy --model` 的 help 文本也列出全部模型 id，但**不含 credits**，所以只能当列表兜底。
- CLI 直接跑会 `Authentication required`（未登录）或 `EADDRINUSE 60679`，别靠 CLI 命令取数。

### 实现

- `src/agents/modelCatalog.ts`：`parseCredits` / `readModelCatalog` / `pickPreferredWorkbuddyModel`
- `src/config.ts`：`DEFAULT_WORKBUDDY_MODEL = 显式配置 || pick(...) || ''`
- 三个条件缺一不可：目录含 `gpt-*`（证明完整）、目标模型存在、`credits === 0`（null 不算免费）

**为什么要求 gpt-* 存在**：它是「拿到完整目录」的信号。残缺目录下直接判断目标模型，
可能在只下发了部分模型的账号上误判。

**为什么 credits 必须是严格的 0**：`""`（未填）和 `null` 都不能当免费，否则账单不可预期。

### 验证

- `npm test` **150/150**，`npm run typecheck` 干净

## 「Failed to fetch」= 服务在运行中被重启（11:02 排查）

**结论**：不是服务 bug，是进程重启切断了进行中的请求。

证据链（`~/.vocal-saga-local-agent/documents/<pid>/project.sqlite`）：

- `translation_runs` 最后一条 `501617b7…`：`created_at 02:53:56Z`（本地 10:53:56），
  65 段、5 批，`plan.ready`/`batch.started` 都写了，之后**没有任何后续事件**（模型调用还在飞）。
- 同一 run 的 65 条 `run_segments` 全是 `pending`、`attempts=1`、
  `updated_at 03:01:34.508Z`（本地 11:01:34）——这是 `recoverInterruptedRuns()`
  在**启动时**把 `running→pending` 打的时间戳，等于服务启动时刻。
- 该函数同时把 run 置 `paused` + `error='服务重启后等待恢复'`。
- 进程树 `npm start`(13543) → tsx(13566) → node(13567)，`TERM_PROGRAM=Apple_Terminal`，
  DiagnosticReports 里没有 node 崩溃报告 → 是**手动重启**，不是崩溃。
- 旧 run 的 65 段一段都没跑完，所以界面显示 `0/65 段`。

浏览器侧：服务一死，页面 800ms 轮询 `/runs/<id>` 的 fetch 直接抛
`TypeError: Failed to fetch`，`App.vue:4201` 把它当 `error.message` 原样显示。

**修的代码**（fanyi-extension）：
`documentWorkspaceClient.ts` 新增 `describeNetworkFailure()`，`workspaceApi` 里
`fetch(...).catch(...)` 把传输层失败包成 `WorkspaceApiError(msg, 0)`：
文案带 base URL + 「服务可能未启动或正在重启」+ 原始错误。`status=0` 不会和 404 混淆
（404 是「项目不存在就新建」的判据，不能被传输层失败触发）。
测试 `documentWorkspaceClient.test.ts` 11/11，扩展全量 551/551。

**排查提示**：以后遇到这类「只有一句 Failed to fetch」，先查 `project.sqlite` 的
`run_segments.updated_at` 是不是恰好等于进程启动时刻。

## 新增：CodeBuddy 连通性自检脚本 + 找到「模型没传下去」的真因

**脚本**：`local-agent-service/scripts/check-codebuddy-connectivity.mjs`
（`npm run check:codebuddy`，`--dry` 只查配置不花钱，`--timeout=ms`）。

七段：配置 → 模型目录 → CLI 定位 → `sdk.query` 一次性 → 池化会话 → 读 CLI 日志核对真实模型
→ HTTP 探活 + `POST /v1/chat/completions` 端到端。

**关键手法**（比看服务日志可靠得多）：
- `pgrep -fl codebuddy-headless` 直接看 CLI 进程的 `--model`。参数顺序是
  `--verbose --model <x> --permission-mode`，**没有 `--model` 就是没传**。
- `~/.codebuddy/logs/<date>/workspace__*.log`：`Sending request: ... model=` 是真实请求模型；
  `runner.run START/DONE` 间隔 2ms 说明 agent 空转、根本没发请求。
- `ModelConfig ... requestOptions.model=<none>` 也是同一个信号。

**真因**：`LOCAL_WORKBUDDY_MODEL=auto` 被当成真实模型 id → `parseAgentModel` 把 `'auto'`
归一成空串 → CLI 没有 `--model` → 静默用账号默认 `hy4-preview`（0.29 credits）。
修法：`modelCatalog.resolveWorkbuddyModel()` 把 `auto`/空值统一交给目录挑选；
`server.ts` 启动时打印 `workbuddy model:`，让「空模型」不再无声。

**沙箱陷阱**：进程环境里有 `CODEBUDDY_SESSION_ID`（被 IDE/Agent 托管）时，
本进程 fork 的 CLI 子进程会静默退出——不写日志、不发请求、stream 789ms 就结束。
脚本据此把 SDK 阶段降级成警告；验证真实模型调用必须在普通终端跑。
