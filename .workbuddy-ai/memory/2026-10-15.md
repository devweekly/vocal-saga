## `local-agent-service` 文学审校 502「Workbuddy 返回了空内容」根因（只读诊断，未改代码）

**现象**：`POST /api/translate/document/literary/review` 间歇性 502，错误
`Workbuddy 返回了空内容，会话已丢弃重建；请重试该批次`，栈顶
`WorkbuddySessionPool.runPrompt`（`workbuddyPool.ts:243`），`durationMs≈49s`。

**根因**：`runPrompt` 把「没有 assistant text」当成会话已坏。
但在 JSON 模式（`--json-schema`）下，成功的一轮是 `StructuredOutput` **tool_use**
块 + `result.structured_output`，**根本没有 text 块**（SDK `types.d.ts`：
`TextContentBlock` 与 `ToolUseContentBlock` 是两种不同 content block）。
`runPrompt` 只读 `part.type === 'text'`，于是原生 structured output 成功也被判为「空」。

**同一操作两条路径相反结果（最硬的证据）**：
- `runWorkbuddyStructured` **无** sessionScope → `queryWorkbuddyRaw`（`workbuddy.ts:57`）
  —— **没有**空文本检查，原生 structured_output 直接可用 → 成功。
- `runWorkbuddyStructured` **有** sessionScope → `pool.runPrompt` → 空文本检查 → 抛错。
  文学分析/审校只要传了 `documentSessionId` 就会走后者。

**为什么没被测试抓住**：`tests/server.test.mjs:232-235` 的桩同时吐
`{type:'text'}` 和 `structured_output`，从没构造过「只有 tool_use、没有 text」的形状。
`runPrompt` 目前也拿不到 schema/mode 信息（`acquire` 只存了 `schemaKey`，`runPrompt` 不读）。

**附带损害**：误判后 `dropSession` 干掉一个健康会话 → 下一单重付 CLI 启动开销，
且 `isFresh()` 使首轮重新注入完整 system prompt（文学审校约 1.6k + 最多 30k 的
memory JSON），表现为「连续空转 15-20s」。

**日志里的两个红鲱鱼**：
- `inputChars=0` —— `requestMetadata()`（`db.ts:135`）按 chat-completions 的 `body.messages`
  算，文学端点传的是 `body.segments`，所以恒为 0，**不代表 prompt 为空**。
- `status=502` —— catch 块的兜底默认值（`routes.ts:311`），不是上游 HTTP 状态。
- `outputChars=0` —— 失败发生在赋值 `output`（`routes.ts:297`）之前。

**修复方向（未实施）**：抛空前先看 `structuredOutput !== undefined`；把 schema/mode
传进 `runPrompt`，让空文本守卫只对纯文本模式生效；补一个「只有 tool_use」的池测试。

## 移除文档 workspace 的 1,500,000 字符上限（已实施）

**报错**：fanyi-extension 阅读页 `无法准备文档 workspace：文档片段总文本超过 1,500,000 字符上限`
（前缀来自 `App.vue:2199`，内层消息来自本机服务）。

**位置**：`local-agent-service/src/documents/projectStore.ts` 的 `validateSegments`
（原来在 `seen.add(id)` 后累加 `totalChars` 并抛 413）。

**关键耦合**：这个字符上限只是**请求体大小的代理指标**。`ensureDocumentWorkspace`
（`App.vue:1916`）把整本书的片段放进**一个** POST。所以只删检查会立刻撞上
`MAX_BODY_BYTES = 6 MiB`（`config.ts:43`）报 `请求体超过 6 MiB 上限`——
对中文正文（UTF-8 3 字节/字符）1.5M 字符≈4.5MB，只删字符检查几乎没有改善。

**改动（3 个文件）**：
1. `projectStore.ts` —— 删除 `totalChars` 累加与 413 抛出。
2. `config.ts` —— 新增 `MAX_DOCUMENT_BODY_BYTES = 64 MiB`，按 20 MiB 源文件
   （`MAX_DOCUMENT_SOURCE_BYTES`）最坏情况 3 倍推导。
3. `server.ts` —— 在全局 6 MiB 解析器**之前**挂
   `app.use('/api/documents', express.json({ limit: MAX_DOCUMENT_BODY_BYTES }))`；
   413 文案改成按 `req.originalUrl` 选择 6 或 64 MiB。

**body-parser 2.x 的跳过机制（容易踩）**：不是靠 `req._body`（2.x 已无此字段），
而是 `read.js` 的 `onFinished.isFinished(req)` —— 第一个解析器读完流后第二个直接 `next()`。
已用运行时脚本验证：8.9 MiB 的 `/api/documents` 请求 201，非文档路由 7 MiB 仍 413。

**没动的相邻上限（都是有理由的，别再顺手删）**：
- `projectStore.ts` 的 **20000 片段条数上限** —— 用户是**先**过条数检查再累加字符，
  既然他们拿到的是字符报错，说明片段数 ≤ 20000，条数上限不是本次阻塞点。
- `lib/translate/document/index.ts` 的 `MAX_STRUCTURED_TEXT_CHARS = 1_500_000` +
  `MAX_STRUCTURED_SEGMENTS = 20_000` —— 同名常量，但属于**已部署的 vocal-saga
  Worker**（`POST /api/translate/document[/segments]`），是公网端点、与扩展 workspace
  路径无关，风险面不同，**未改**。

**验证**：
- `local-agent-service` 新增回归测试
  `tests/document-project.test.mjs :: a document whose segments exceed 1,500,000 characters is imported in full`。
  做过变异验证：把守卫加回去 → 该测试立刻变红。
- `npm run typecheck` 干净；`npm test` 43 项 42 过。
- ⚠️ 唯一失败 `manual acceptance is newer than an older candidate and is not auto-staled by
  Prompt changes`（`document-project.test.mjs:123`）**在 HEAD 上就失败**，与本次改动无关
  （已用 `git checkout HEAD --` 三个文件后复现确认）。

## 修复上述失败用例：毫秒时间戳打平导致旧候选覆盖新人工修订（已实施）

**它不是「测试本身有问题」，是真实排序缺陷。** 先复现：单独跑测试体时通过
（候选 `.796Z`、人工 `.798Z`，差 2ms），但在测试跑者里 **6 次跑 4 次红** —— 说明是竞态。
再单独跑 `--test-name-pattern="manual acceptance is newer"` 6 次：**4 红 2 绿**，确认 flaky。

**根因**：`acceptCandidates` 用
`created_at > 候选.created_at` 判断「有没有更新的人工修订」。
`created_at` 是 `new Date().toISOString()`，**毫秒精度**。同一毫秒内落库的候选与人工修订
时间戳相同 → 严格大于为假 → 旧候选获胜并覆盖人工修订。

**两处修复（互补）**：
1. `isoNow()` 改为**进程内单调递增**（`Math.max(Date.now(), lastStampMs + 1)`）。
   消掉同进程内的打平，顺带让所有 `ORDER BY created_at` 的站点受益。
2. `acceptCandidates` 的新旧判据改用**插入顺序 `rowid`**。
   跨进程也会打平（本机服务与 CLI 可能同时打开同一个项目库），时间戳靠不住。
   已确认 `projectStore.ts` 里**没有任何 `DELETE FROM`**，所以 `rowid` 就是可靠的插入序。
3. 另外给 5 处「哪条译文是当前版本」的排序补了 `rowid DESC` 兜底：
   `getSegments` 的 accepted/candidate 两个子查询、`latestAccepted`（文学记忆校验）、
   `createRun` 的 stale 规划、`verifyProject`。

**新增 2 个回归测试（`document-project.test.mjs`）**：
- `a manual edit inserted after a candidate wins even when both share one created_at millisecond`
  —— **直接改库把两条记录的 created_at 改成完全相同**，把打平路径固定下来（否则单调时钟
  会让这条路径再也无法自然触发）。
- `created_at is strictly increasing across back-to-back writes` —— 120 次背靠背写入必须严格递增。

**验证**：原 flaky 用例 **15/15 通过**；全套 **45/45**；typecheck 干净；
变异测试 **2/2 捕获**（把 rowid 判据换回 created_at → 第 1 条变红；把单调时钟换回裸
`Date.now()` → 第 2 条变红）。改动前那批文档上限的运行时脚本仍 7/7。
