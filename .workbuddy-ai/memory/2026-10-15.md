# 2026-10-15

## `local-agent-service` 文学审校 502「Workbuddy 返回了空内容」根因（只读诊断，未改代码）

**现象**：`POST /api/translate/document/literary/review` 间歇性 502，错误
`Workbuddy 返回了空内容，会话已丢弃重建；请重试该批次`，栈顶
`WorkbuddySessionPool.runPrompt`（`workbuddyPool.ts:243`），`durationMs≈49s`。

**根因**：`runPrompt` 把「没有 assistant text」当成会话已坏。
但在 JSON 模式（`--json-schema`）下，成功的一轮是 `StructuredOutput` **tool_use**
块 + `result.structured_output`，**根本没有 text 块**（SDK `types.d.ts`：
`TextContentBlock` 与 `ToolUseContentBlock` 是两种不同 content block）。
`runPrompt` 只读 `part.type === 'text'`，于是原生 structured output 成功也被判为「空」。

**同一操作两条路径相反结果（最硬的证据）**：
- `runWorkbuddyStructured` **无** sessionScope → `queryWorkbuddyRaw`（`workbuddy.ts:57`）
  —— **没有**空文本检查，原生 structured_output 直接可用 → 成功。
- `runWorkbuddyStructured` **有** sessionScope → `pool.runPrompt` → 空文本检查 → 抛错。
  文学分析/审校只要传了 `documentSessionId` 就会走后者。

**为什么没被测试抓住**：`tests/server.test.mjs:232-235` 的桩同时吐
`{type:'text'}` 和 `structured_output`，从没构造过「只有 tool_use、没有 text」的形状。
`runPrompt` 目前也拿不到 schema/mode 信息（`acquire` 只存了 `schemaKey`，`runPrompt` 不读）。

**附带损害**：误判后 `dropSession` 干掉一个健康会话 → 下一单重付 CLI 启动开销，
且 `isFresh()` 使首轮重新注入完整 system prompt（文学审校约 1.6k + 最多 30k 的
memory JSON），表现为「连续空转 15-20s」。

**日志里的两个红鲱鱼**：
- `inputChars=0` —— `requestMetadata()`（`db.ts:135`）按 chat-completions 的 `body.messages`
  算，文学端点传的是 `body.segments`，所以恒为 0，**不代表 prompt 为空**。
- `status=502` —— catch 块的兜底默认值（`routes.ts:311`），不是上游 HTTP 状态。
- `outputChars=0` —— 失败发生在赋值 `output`（`routes.ts:297`）之前。

**修复方向（未实施）**：抛空前先看 `structuredOutput !== undefined`；把 schema/mode
传进 `runPrompt`，让空文本守卫只对纯文本模式生效；补一个「只有 tool_use」的池测试。
