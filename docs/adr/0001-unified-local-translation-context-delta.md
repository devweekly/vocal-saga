# ADR-0001: 统一本地翻译管线与初译上下文增量

- 状态：Accepted
- 日期：2026-10-17
- 相关文档：[Local Agent 文档/小说统一翻译 Pipeline](../TRANSLATION_PIPELINE.md)

## 背景

本地文档翻译有多个用户入口：阅读页的继续翻译/强制重译、Agent Workspace、CLI 和项目 API。入口必须使用同一套项目级执行生命周期，而不能随着入口不同切换为另一套翻译/记忆实现。

小说人物和称谓会在多章中反复出现。仅在整书预分析阶段生成 Context Graph 不能覆盖翻译时新识别的别名、称谓、指代与关系；而只让初译返回译文，会丢失模型在当前段落中新观察到的上下文。当前批次并发读取同一基础记忆，也意味着当新实体在翻译过程中首次出现时，其他尚未开始的批次没有统一且可复现的更新机制。

## 决策

### 1. 所有本地文档入口共享一个 Run executor

阅读页、Agent Workspace、CLI 和项目 API 都通过 Document Project / Run 进入 `startProjectTranslationRun → executeRun → processBatch`。UI 只能选择翻译范围、策略和显示方式，不允许在扩展侧新增第二套本地模型调用循环、实体合并逻辑或记忆写入方式。

统一的是执行生命周期、结构验证、候选译文、持久化、审校、停止/恢复与审计；任务类型仍可使用不同 Prompt 与策略。Cloudflare Worker 的短请求运行时不属于这条本地文档管线。

### 2. 初译响应包含译文和有界上下文增量

文学初译返回必需的 `translations`，并应同时返回 `context_delta`，结构包括：

- `entity_candidates`：新实体、人物称谓、别名和候选译名。
- `entity_mentions`：当前原文片段和实际译文中可定位的实体提及。
- `relationship_deltas`：带原文证据的候选关系变化。
- `open_questions` 与 `conflicts`：保留不确定性，不强迫模型给出确定结论。

初译上下文增量只是建议。服务端独立验证增量和译文；无效上下文元数据不得导致有效译文丢失。

### 3. 增量必须有来源证据并受批次边界约束

每个证据都要引用当前请求的 segment ID 和该 segment 中可核验的连续原文。实体规范名称必须出现在其证据中；别名必须有本批证据；entity mention 的目标表面形式必须在同一 segment 的实际译文中。关系双方需能在证据片段中定位，但模型对关系谓词的解释仍是候选，需要后续审查。

不得用模型自称的置信度、confirmed 状态或自由文本理由跳过这些检查，也不允许引用前文参考区以外的后文信息作为当前批次证据。

### 4. 使用冻结波次控制动态上下文的可复现性

每个波次最多并行执行配置允许的批次数量。波次开始时构造同一份上一波上下文投影；本波所有批次都读取相同的 TranslationBrief 基础状态。只有整波处理完成后，才按来源 ordinal 归并其增量，供下一波使用。

这是一项刻意的同步边界：不能在模型请求完成时立即改变共享记忆，否则响应的网络时序会决定其他批次看到什么；也不能让当前章节的后文或后续章节知识泄漏到来源顺序更早的批次。

### 5. 将候选和证据写入 Run 账本，最后才投影到项目记忆

已核验的上下文增量按 Run 和首个 source segment 幂等保存到 SQLite `translation_context_deltas`，记录 batch index、来源 ordinal、片段 ID、增量和验证摘要。暂停、重试或进程恢复可以重建 source-ordered run-local 上下文。

仅在文学 Run 完整结束且当前来源 revision 与 Run 的来源 revision 一致时，将候选合并到当前项目文学记忆；新增人物/关系保持 suggested，并保存带 segment ID 与原文引文的 `evidenceRefs`。后续 TranslationBrief 必须根据证据 segment 的 source ordinal 过滤记忆：称谓曾在早期出现，不代表后文产生的实体解释可以回流到早期上下文。人工确认的目标译名不被覆盖。如果来源已变更或 Run 中断，增量保留在 Run 账本，但不写入当前项目记忆。

### 6. 用一致性审计发现冲突，不自动修订译文

当多个批次对同一规范来源名称提出不同译名时，按来源顺序保留第一个候选，并记录 open question；质量审计额外生成 `context-delta-conflict` finding。审计只定位问题并提供证据，不能自动替换全书译文，也不能修改已采纳或人工修订的内容。只有现有显式人工采纳/返工流程可以改变译文。

## 后果

正面影响：

- 阅读页、Workspace 和 CLI 共享同一执行与记忆边界，不会出现只有某个入口支持上下文一致性的情况。
- 角色/称谓在初译中被识别后，可以从下一波开始被复用，而不必等到重新运行整书预分析。
- 每次动态更新都有 Run、source segment 和可核验引文；重启、重试及审计可以追溯该信息从哪里产生。
- 同波上下文被冻结，结果不依赖模型请求完成顺序；人工确认和已采纳译文仍保持最高优先级。

代价与限制：

- 波次间有同步屏障，不能做到全书所有批次同时运行。通过有界并发控制每波大小，在一致性与吞吐量之间取舍。
- context_delta 是额外的结构化输出，会占用一部分模型输出预算；字段数量和证据长度必须受限。
- 引文存在不等于模型的关系解释一定正确。因此实体译名、人物身份和关系候选都保留人工复核状态。
- 旧模型或旧 Provider 若未返回 context_delta，译文仍可保存，但该批不会产生新的动态上下文信息；事件会反映接受/拒绝数量。

## 考虑过的替代方案

| 方案 | 不采用原因 |
|---|---|
| 模型返回后立刻修改共享记忆 | 并行批次的可见上下文由响应时序决定，难以复现，存在来源顺序和剧透边界风险 |
| 只依赖整书预分析 Context Graph | 无法覆盖翻译时才发现的别名/称谓，也不能将当前段落的观察立即反馈给后续批次 |
| 在浏览器扩展中独立解析/合并上下文 | 会让阅读页与 Workspace/CLI 产生两套状态与信任边界；本地服务应是唯一事实来源 |
| 将全部文学批次改为串行 | 简单但失去有界并发的效率；波次机制保留并发，同时让上下文只在确定的边界发生变化 |

## 验收与回归

- 验证伪造、缺失和跨批次原文引文不会变成上下文事实。
- 验证实体提及的目标字符串真实出现在同一片段译文中。
- 验证确认译名在冲突候选到达后保持不变，冲突进入 open questions/审计。
- 验证同一波上下文冻结，下一波只能读取较早 source ordinal 的上下文增量。
- 验证来源 revision 变化或 Run 未成功结束时，不把旧 Run 的候选写入当前项目记忆。
- 验证阅读页、Agent Workspace、CLI 和项目 API 仍使用同一个 Run executor。
