# 2026-10-15 WorkbuddySessionPool 结构化输出误判

## 用户报告与根因

排查本机 Local Agent Service 的 Workbuddy Session 池时，发现 `local-agent-service/src/agents/workbuddyPool.ts` 的 `WorkbuddySessionPool.runPrompt()` 在收到流结束后只检查累计的 assistant 文本；文本为空就认为会话损坏、执行 `dropSession()` 并抛错。但开启原生 `--json-schema` 的 structured output 时，成功响应可以只通过 SDK 的 `StructuredOutput` 工具调用返回，不保证先输出 `type: 'text'` 的 assistant 内容。

关键路径：
- `workbuddy.ts` 中不带 `sessionScope` 的 structured 调用走 `queryWorkbuddyRaw()`，直接读取 `result.structured_output`。
- 带 `sessionScope` 的文学分析/审校会 acquire 有 schema 的池槽位，然后走 `pool.runPrompt()`；当前池函数收集 result.structured_output，但无条件要求 `text.trim()` 非空，导致两条路径对同一个合法响应行为不一致。
- `Slot.schemaKey` 已保存当前槽位是否使用 schema（空字符串表示纯文本模式），可以用来让空文本守卫只作用于纯文本通道。
- 对 structured 模式，`structuredOutput !== undefined` 是成功结果；不能因为 text 为空就丢弃健康会话。纯文本模式的空输出守卫仍应保留。
- SDK content block 中 `text` 与 `tool_use` 是不同形状；测试必须覆盖 assistant content 仅含 `tool_use` 且 result 带 `structured_output` 的响应。
- 误判的附带代价是关闭健康 SDK Session，使下次调用支付 CLI 启动和 system prompt 重新注入开销。

## 诊断日志的解释

- `inputChars=0` 由 `requestMetadata()` 按 chat-completions 的 `body.messages` 计算；文学分析/审校输入使用 `body.segments`，所以此指标为 0 不代表模型输入为空。
- 这类端点的 `status=502` 是服务端 catch 的默认映射值，不等于上游真实返回 502。
- `outputChars=0` 可能因为异常在最终输出赋值前抛出，并不单独证明模型未输出 structured result。
- 约 49 秒的调用耗时小于默认 180 秒请求超时，不能仅凭耗时判断发生超时；应区分结构化输出误判、真实 SDK error 和 timer timeout。

## 修复/验收要求

1. 在 `WorkbuddySessionPool.runPrompt()` 中根据 structured result 和 slot schema/mode 区分成功条件：原生结构化结果存在时不能因空文本失败；纯文本模式仍拒绝真正空输出。
2. 不能把合法 structured output 判为 poison session，也不能在成功情况下调用 `dropSession()`。
3. 为 `WorkbuddySessionPool.runPrompt()` 增加直接回归测试：assistant content 只有 `tool_use`、result 带 `structured_output`，应返回成功、保留会话并增加 uses。
4. 增加对照测试：纯文本模式只有 `tool_use`/没有文本且无 structured result 时仍然失败并销毁会话；结构化模式在既没有文本也没有 structured result 时仍然失败。
5. 运行 `cd local-agent-service && npm test && npm run typecheck`，并检查 GitHub Actions 的 Local Agent Service 和主 CI。
6. 先记录在项目记忆，再修代码；修复遵循 AGENTS.md：关键改动有测试，提供足够中文注释。

本条记忆记录的是当前诊断和验收契约；仅在代码与 CI 验证实际完成后，再追加修复提交与测试结论。
